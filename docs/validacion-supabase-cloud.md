## Cuentas persistentes mediante variables de entorno

El modo `--persistentes` inicia sesión con tres cuentas ya creadas y confirmadas en NEXU-TEST. No crea cuentas, cambia roles ni crea cursos. Auth valida la contraseña y el ejecutor comprueba el correo confirmado, el UUID y que las tres identidades son distintas. Los metadatos editables no otorgan privilegios. Este modo no demuestra por sí solo las políticas de autorización.

Se necesitan `NEXU_TEST_ANON_KEY` y, para cada uno de `ADMIN`, `FACILITADOR` y `PARTICIPANTE`, las variables `NEXU_TEST_<ROL>_EMAIL` y `NEXU_TEST_<ROL>_PASSWORD`. La clave debe ser la clave pública del proyecto NEXU-TEST. El proceso no imprime credenciales ni JWT. Las variables de entorno pueden ser visibles para otros procesos de la misma cuenta del sistema, por lo que hay que usar una máquina y una cuenta de sistema confiables. No guardar valores en el repositorio, argumentos de comandos, historial ni logs.

En esta instancia de Codex Cloud el estado consultado no muestra secretos configurados y no se ofrece una herramienta para añadirlos o persistirlos entre tareas. Si en la configuración del entorno de Codex aparece una sección de secretos y permite guardar variables para tareas futuras, se pueden introducir allí desde el navegador sin escribirlas en el chat; verificar que el entorno nuevo reciba las siete variables. Esta capacidad no se ha comprobado en Android.

Una alternativa es Termux en Android y un gestor de contraseñas. Guardar las tres contraseñas distintas y robustas en el gestor. En una sesión privada de Termux, introducir cada valor desde el gestor mediante `read -rs NOMBRE` seguido de `export NOMBRE`, sustituyendo NOMBRE por cada variable listada arriba. `read -rs` oculta la entrada y evita que el valor aparezca en el historial; no ejecutar comandos que muestren el entorno. La clave pública y los correos se configuran de igual forma. Ejecutar `python3 supabase/tests/cloud/auth_rls_session.py --persistentes` desde el repositorio. Las variables se pierden al cerrar Termux, pero los valores permanecen en el gestor y pueden cargarse de nuevo.

La cuenta existente debe usar el flujo legítimo de recuperación de Auth si su contraseña se desconoce. Las cuentas ausentes deben registrarse mediante Auth y confirmar sus correos legítimamente. Antes de activar los fixtures y el bootstrap para estas identidades se requiere autorización específica y verificación independiente de los UUID; el bootstrap histórico por marcador no admite automáticamente cuentas persistentes. El modo `--persistentes-con-fixtures` requiere una terminal interactiva y confirmación explícita, comprueba que la identidad administrativa ya tenga el rol y crea cursos y relaciones ficticias. No elimina datos creados. Revisar primero las políticas, el destino fijo NEXU-TEST y los datos que se crearán.
